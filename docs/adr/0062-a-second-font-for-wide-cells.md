# ADR 0062: A wide cell is drawn from a second, 16×16 font

- Status: accepted
- Date: 2026-10-10
- Scope: glyph storage, both renderers, the shipped font set

## Context

Blit's terminal engine already handles wide characters correctly as *state*:
the Unicode 15.1 width table ([ADR 0007](0007-unicode-width-table.md)) gives a
CJK ideograph two cells, the second carries `BLIT_ATTR_CONTINUATION`, and
`GET /v1/surfaces/{id}/cells` reports `"width": 2`. A client reading the API
sees exactly the right thing.

The pixels were wrong. The primary font is `Blit-Hibr-Terminus16.psf`: PSF2,
929 glyphs, **8×16**. Every codepoint it does not map resolves to the `?`
substitute in `blit_font_glyph_index`, so a desktop showing Chinese text
showed `??`, which is how this was reported from the live host: *"there are no
chinese characters, there are two big ??(s)"*.

Two separate problems hide behind that one symptom, and only the first is
about coverage:

1. **Coverage.** 929 glyphs cannot include CJK. Covering the wide BMP blocks
   needs about fifty thousand.
2. **Cell size.** A wide character occupies two 8-pixel cells, so its glyph
   needs a **16×16** bitmap. PSF2 stores one cell size per file, and the glyph
   store had no notion of a second one. Even a present CJK glyph would have
   had nowhere to live: the renderers asked for a two-cell-wide destination
   and got an 8-pixel bitmap stretched to fill it.

So this could not be closed by regenerating the existing artifact with more
glyphs, which is why it waited for a decision.

## Options considered

1. **One font, more glyphs.** Fails on cell size: the file would still be
   8×16 and every wide glyph would be a stretched narrow bitmap.
2. **A runtime fallback chain**, consulting system fonts for unmapped
   codepoints. Rejected: [ADR 0020](0020-font-fallback-coverage.md)
   deliberately resolves fallbacks at *build* time so a runtime installation
   has no font-tool or font-package dependency and cannot render differently
   on two hosts. A runtime chain would reverse that.
3. **Declare it a non-goal** and render unmapped wide codepoints as a visibly
   distinct placeholder rather than `?`. Honest, and strictly better than
   today, but it answers a report about missing Chinese text with a nicer
   box.
4. **A second, 16×16 PSF2 consulted for wide cells, resolved at build time.**
   Chosen.

## Decision

A wide cell is drawn from a second font.

- `assets/fonts/Blit-Hibr-Unifont16.psf` is 16×16 and holds 49,899 glyphs:
  every wide block of the BMP, complete. It is generated by
  `tools/fonts/make-wide-psf.py` from GNU Unifont's BDF, taking only glyphs
  marked `DWIDTH 16`, and checked in — the same contract as the primary font,
  so an installation still needs no font tooling. Unifont is redistributed
  here under the **SIL OFL 1.1**.
- The engine keeps one notion of a cell. The wide font is consulted only for a
  cell the width table already made two columns wide, so nothing about layout,
  damage or the API changes.
- A wide codepoint the wide font does not map still falls back to the primary
  font's substitute. The substitution is now reachable only for genuinely
  uncovered codepoints rather than for all of CJK.

**The SDL glyph atlas is populated on demand.** A static atlas over 49,899
tiles of 18×18 would be a 2304×7020 texture, about 65 MB uploaded at startup
for glyphs a given session will almost never use. Instead the wide atlas is a
fixed 2048×2048 — 12,769 slots — filled one glyph at a time on first use, with
a direct codepoint-indexed slot table so the lookup is O(1). There is no
eviction: twelve thousand distinct wide characters on one display exceeds any
realistic document, and if the atlas does fill, further new glyphs fall back to
the substitute rather than evicting something visible. The KMS renderer needs
no atlas; it reads bitmap rows directly and simply takes the other font.

Wide glyphs batch separately from narrow ones, because a batch submits with a
single texture.

## Consequences

CJK, Kana, Hangul, Fullwidth forms and CJK symbols render as themselves on
both renderers. The package grows by 1.71 MiB, which is the cost of carrying
the coverage rather than depending on the host's fonts.

**Not covered: anything outside the BMP**, which means emoji. `unifont.bdf` is
a BMP font; plane 1 lives in Unifont's `unifont_upper`, a third artifact and
another 1–2 MiB. Emoji in a terminal also want colour, which a PSF2 bitmap
cannot express at all, so a monochrome emoji glyph is a partial answer to a
different question. Deferred deliberately, and the `?` substitute remains
visible there — the one place the original report is still accurate.

Combining marks, bidi and shaping are unchanged and remain out of scope: the
engine stores combining marks per cell and draws them over the base glyph, and
Hibr performs right-to-left ordering ([ADR 0034](0034-hibr-adapter-input-only-stream.md)).

## Evidence

`tools/tests/wide_glyph_gate.rb` prints a CJK ideograph, a Hiragana syllable,
a Hangul syllable and a fullwidth form, and asserts each occupies two cells in
the canonical state *and* renders as a shape distinct from the `?` substitute
and from the other three. The pre-change binary renders all four as `?`, so
all four shapes are identical and the gate fails on the first comparison.

`tools/tests/font_identity_gate.rb` asserts the wide font's identity the way
it already does the primary font's, so a stale or absent wide artifact fails
loudly rather than silently returning to `?`.
